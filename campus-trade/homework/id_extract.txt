校园二手交易微信小程序软件系统的需求构思及描述
1. 背景介绍
高校里有大量仍能使用的闲置物品。教材、宿舍小家电、数码配件等在学期末和毕业季集中出现，但线下跳蚤市场开放时间有限，微信群和校园墙的信息又很容易被新消息覆盖。
校园交易的特点是距离近、金额通常不高，学生更愿意在宿舍楼、食堂或教学楼附近完成面交。通用二手平台覆盖范围大，却很难细分到校区和楼栋，也无法确认对方是否为本校学生。
商品照片同样会影响交易。宿舍和楼道光线较暗，卖家随手拍出的图片容易模糊，买家看不清划痕、污渍和型号，后续就可能因为成色描述不一致产生争议。
我们计划采用 uni-app 开发微信小程序，后端使用 Spring Boot，MySQL 保存业务数据，Redis 处理缓存、会话和并发控制，并接入多模态大模型 API 辅助识别商品和生成描述。系统的重点不是堆叠功能，而是让校园交易更方便、更可信。
2. 主要问题
一、交易和用户需求
信息分散且状态更新不及时：同一件商品可能出现在多个群聊中，卖出后仍有人询问；买家真正需要商品时，又很难找到几天前发布的信息。
价格和成色缺少参考：学生往往不了解折旧情况，同类商品定价差异较大。照片不清楚、描述过于简单时，买卖双方还需要反复确认细节。
身份与联系方式存在风险：校外人员可以进入普通交易群，私下交换手机号或微信后也容易受到骚扰。平台需要确认校园身份，但不能因此收集过多个人信息。
低价商品不适合复杂流程：旧教材、文具等价格不高，如果发布、沟通和交接耗时太长，用户很可能直接放弃。因此操作步骤必须尽量简洁。
供求出现的时间不一致：卖家发布时可能没人需要，买家想购买时又找不到合适商品。只有“出售”入口还不够，还需要保留求购信息并持续匹配。
二、系统实现问题
交易状态必须保持一致：热门商品可能被多人同时预约。如果只在页面上改变状态，而数据库没有正确锁定，就会出现重复交易。
毕业季访问量会突然增加：大量用户集中浏览和上传图片，容易造成接口变慢。热门数据可以放入 Redis，但缓存和 MySQL 之间也要避免出现不一致。
校园网络并不总是稳定：在宿舍楼或地下空间上传图片时可能中断，系统需要处理重复提交、上传失败和请求重试，不能让用户重新填写全部信息。
图片存储和外部接口会增加成本：商品通常包含多张照片，大模型 API 也按调用量计费。系统需要限制图片大小，避免重复调用，并在接口不可用时保留手动发布功能。
消息提醒可能被忽略：买家发出咨询后，如果卖家没有及时进入小程序，交易机会很快就会过去。但微信订阅消息需要用户主动授权，平台不能假设每条消息都能送达。
三、安全与人工智能风险
账号和接口可能受到攻击：攻击者可能批量注册、越权查看订单、修改商品状态或上传异常文件。后端不能只依赖前端传来的参数。
大模型的结果不一定正确：模型可能认错教材版本、品牌和商品成色，也可能根据不清楚的图片补充并不存在的细节。AI 结果只能作为建议。
第三方服务存在不确定性：校园认证、大模型 API、对象存储和微信订阅消息都可能出现故障，因此核心的浏览、发布和交易流程不能完全依赖单一外部服务。
审核任务容易集中：毕业季商品数量上升时，违规内容、举报和身份材料可能同时出现。完全依靠人工会处理不过来，完全依靠模型又容易误判。
四、运营与校园管理
校园交易有明显的淡旺季，开学和毕业阶段活跃，假期则较冷清。平台初期还会遇到商品少、用户少的问题，需要先在一个校区小范围试用。
平台还要处理违禁商品、虚假图片、恶意差评和面交纠纷。不同学校的管理要求不完全相同，规则应当可以配置，而不是写死在程序中。
3. 软件创意
本项目的思路是把微信小程序的低使用门槛、Spring Boot 的业务处理能力、MySQL 与 Redis 的数据管理能力，以及大模型 API 的图文理解能力结合起来。功能设计以真实校园场景为依据，优先解决发布慢、信息不清和交易状态混乱的问题。
一、智能发布
拍摄质量提示：用户选图后，小程序先检查亮度和清晰度。图片过暗或模糊时，页面提醒重新拍摄或补充正面、背面和瑕疵位置。
自动填写商品信息：后端对图片进行压缩和基础处理，再调用多模态大模型 API，生成商品类别、标题和简短描述。用户确认后才能发布，所有字段都允许修改。
缺失信息追问：如果用户只上传一张正面照片，系统不会直接拼出完整介绍，而是结合商品类别追问版本、尺寸、是否维修等关键内容。回答可以选择跳过，避免发布流程变得太长。
成色与价格参考：系统把卖家填写的使用时间、商品成色和同校历史价格结合起来，给出一个价格区间。该结果只用于减少盲目定价，不代替双方协商。
校园商品词库：教材简称、课程名称和宿舍用品在普通商品库中不一定准确。平台可以维护一个小型词库，用于纠正大模型容易混淆的分类和关键词。
图片与描述核对：如果图片中出现明显磕碰，而文字写着“无划痕”，系统提示卖家重新检查。模型判断不清楚时直接显示“不确定”，不强行给出结论。
人工兜底：大模型 API 超时或返回格式错误时，页面自动切换到普通表单。这样即使智能功能暂时不可用，用户仍能完成发布。
二、交易流程和后端设计
交易状态管理：商品状态分为在售、已预约、待面交、已完成、已取消和申诉中。每个状态只允许执行对应操作，避免随意跳转。
预约锁定与防重复提交：用户预约商品时，Spring Boot 先通过 Redis 完成短期锁定，再写入 MySQL。连续点击或网络重试不会生成多条订单。
候补与自动释放：热门商品被预约后，其他买家可以进入候补队列。预约在规定时间内没有确认，Redis 到期后释放锁定，再按顺序提醒下一位买家。
双向确认面交：买卖双方分别确认交付和收货，双方都完成操作后订单才结束。结果不一致时保留记录，由管理员查看。
自然语言搜索：用户可以输入“预算 200 元以内的键盘”等日常表达。大模型 API 只负责提取类别、价格等条件，真正的商品查询仍由后端完成。
求购反向匹配：买家找不到商品时可以发布求购信息。新商品上线后，后端按照类别、价格和校区进行匹配，再决定是否提醒双方。
热点数据缓存：热门商品、分类和活动配置放入 Redis，订单、用户和商品详情以 MySQL 为准。这样既能提高访问速度，也能明确数据来源。
三、安全和平台治理
校园身份认证：用户通过微信授权登录后，再绑定校园身份。学校无法提供接口时，可以上传经过遮挡处理的校园卡信息，由管理员审核。
最小化收集数据：平台只保存完成交易所需的信息，不公开宿舍号和实时位置。大模型 API 的密钥放在后端，不能写进小程序代码。
反诈与违规提醒：聊天内容中出现“先交保证金”“点击链接付款”等词语时，系统进行风险提示；违禁商品由规则筛查和人工审核共同处理。
分级审核：普通教材和生活用品可以快速发布，高价值数码产品、重复图片和价格明显异常的商品进入人工复核，减少审核人员的无效工作。
上传安全检查：后端限制图片格式、大小和数量，并对文件重新命名和校验，避免用户把其他文件伪装成图片上传。
操作记录：商品修改、预约取消、信用分变化和管理员处理都保留日志。发生争议时可以查看过程，但不会把大模型结果当作最终证据。
四、小程序交互和校园运营
微信快捷入口：用户可以从最近使用的小程序、分享卡片或校园二维码进入平台，不需要下载安装新的应用。
分类拍摄模板：教材提示拍摄封面和版本页，数码产品提示拍摄型号和接口，小家电则补充尺寸和通电情况。
面交二维码：见面后由一方出示短时有效二维码，另一方扫码确认。该功能用于记录双方已经面交，不能替代商品检查。
订阅消息提醒：咨询、预约和订单状态变化通过站内消息展示。用户主动订阅后，再发送微信提醒，避免频繁打扰。
校园专题板块：根据校历开启毕业清仓、新生用品和免费赠送等专区。活动配置保存在 MySQL 中，当前配置缓存到 Redis。
组合发布：对于“教材加习题册”或“显示器加支架”这类物品，卖家可以合并发布并设置整体价格，减少低价值商品逐件沟通的时间。
4. 系统组成和部署
一、系统组成
uni-app 微信小程序端：负责登录、拍照、商品展示、搜索、聊天、预约和个人中心等页面，并调用微信授权、扫码和订阅消息能力。
Spring Boot 后端：提供统一接口，处理身份认证、商品管理、订单状态、消息、评价、举报和权限校验，也是连接数据库和外部服务的核心。
MySQL 数据库：保存用户、商品、订单、评价、举报和操作日志等长期数据。订单与商品状态更新使用事务和约束保证一致性。
Redis：保存登录状态、验证码、热点商品和短期锁。它主要承担加速访问和控制并发的任务，不能代替 MySQL 保存核心交易数据。
大模型 API：接收经过后端检查的图片和文字，返回分类、描述和成色建议。Spring Boot 负责封装调用过程，并设置超时、重试和调用次数限制。
其他服务：商品图片可以存入对象存储；校园身份核验优先对接学校接口。如果暂时无法对接，则保留人工审核流程。
二、部署方式
小程序先以开发版和体验版在校内测试，完成隐私说明、内容管理规则和真机适配后，再提交微信平台审核。
Spring Boot 服务部署在云服务器，通过 HTTPS 提供接口。正式环境与测试环境分开，大模型密钥和数据库密码使用服务端配置管理。
MySQL 定期备份并限制访问来源。Redis 仅允许内网访问，设置过期时间和持久化策略。图片存储设置访问权限，避免直接暴露原始地址。
5. 功能描述
一、用户端功能
登录与认证：用户通过微信授权进入小程序，再完成校园身份验证。系统支持资料修改、账号注销和登录状态管理。
商品发布：用户拍照或从相册选图，填写价格、交易地点范围和联系方式偏好。智能填写失败时可以直接手动发布。
浏览与搜索：首页展示分类、最新商品和校园专题，支持关键词、自然语言、价格和楼栋范围筛选。
商品详情：展示原始图片、卖家确认后的描述、成色、价格、发布时间和信用情况，AI 建议与用户填写内容分开标明。
收藏与求购：买家可以收藏商品，也可以发布求购信息。出现匹配商品时，系统在用户授权后发送提醒。
平台聊天：买卖双方在小程序内沟通，可发送文字、图片和商品卡片。平台对可疑链接和高风险话术进行提示。
订单管理：支持预约、取消、面交确认、完成和申诉，用户可以在订单页查看当前状态和操作记录。
评价与举报：交易完成后双方可以评价。遇到虚假商品、违禁内容或恶意行为时，可提交举报材料。
二、智能辅助功能
图片预处理：对过大的图片进行压缩，对暗光照片做适度提亮，同时保留原图信息，避免处理后的图片掩盖商品真实情况。
信息生成：大模型 API 根据图片生成分类、标题和描述草稿，并把结果转换为固定字段，方便小程序自动填入表单。
辅助判断：系统提供成色、价格区间和图文一致性提醒。结果旁边注明“仅供参考”，发布前必须由卖家确认。
三、管理端功能
管理员可以审核校园身份和举报，处理违禁商品与交易纠纷，并查看必要的操作记录。普通审核员和系统管理员使用不同权限。
运营人员可以调整分类、禁售规则、校园专题和信用分规则，查看商品量、成交量和接口异常情况，但统计结果应先做匿名化处理。
6. 可行性与风险
一、可行性分析
技术上，uni-app、Spring Boot、MySQL 和 Redis 都有成熟的开发资料。大模型能力通过 API 接入，课程项目不需要自行训练和部署大型模型。
开发上，可以先完成登录、商品和订单等基础模块，再接入 Redis 和大模型 API。各阶段可以独立测试，适合小组分工。
使用上，微信小程序无需额外安装，便于在班级群和校园活动中推广。项目可以先面向一个校区试用，根据反馈再增加功能。
二、主要风险
识别结果不准确：暗光、遮挡或相似商品会影响大模型判断。系统通过人工确认、结果标记和手动填写降低影响。
接口费用和稳定性：集中上传图片可能造成大模型 API 超时或费用上升，需要设置限额、缓存和降级方案。
数据一致性：Redis 锁失效或缓存更新不及时可能导致重复预约。订单最终状态应以 MySQL 为准，并对关键流程进行并发测试。
平台审核与适配：交易类小程序需要重视隐私说明和内容治理，不同手机与微信版本也要进行真机测试。
隐私与安全：系统涉及微信身份标识、学号、聊天和交易记录，需要使用 HTTPS、访问控制、脱敏和删除机制，避免过度保存。
