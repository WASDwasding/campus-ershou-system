# 课程开发计划（14 周）

按老师公布的得分节点倒排。原则：**文档周也要写一点能演示的东西；开发周也要改文档。** 对抗赛比的是「交易闭环 + 能防住对方」，不是功能数量。

建议固定每周一次短会（30～45 分钟）：上周完成了什么、卡在哪、本周谁交什么。

---

## 角色（5 人）

| 角色 | 主责 | 文档时干什么 |
| --- | --- | --- |
| 组长 | 进度、仓库、云服务器、统稿、合并 PR | 每份得分文档的目录和终稿 |
| 鉴权 | 注册登录、JWT、用户资料 | 用例：注册/登录/越权 |
| 交易 | 商品、下单、库存 | 超卖、价格篡改相关需求与设计 |
| 支付与前端主流程 | 模拟支付、Vue 交易页 | 支付绕过、页面原型 |
| AI 与安全 | 定价/议价、Burp、渗透记录 | OWASP 对照表、攻防报告 |

一个人可以兼「支付与前端」或「AI 与安全」里较轻的一块；**不要五个人同时改同一张订单表。**

---

## 总览（倒排）

```
W1  构思        ── 交「需求构思及描述」
W2  调研+范围冻结
W3  计划书      ── 交「项目计划书」（可基于本文改一版）
W4  立项答辩    ── 交立项材料 / 答辩 PPT
W5  SRS         ── 交「需求规格说明书」
W6  需求评审    ── 评审纪要；此后需求原则上冻结
W7  详细设计草稿 + 登录可跑
W8  设计说明书  ── 交「软件设计规格说明书」
W9  商品+下单
W10 支付+IM 或 AI 二选一先做完
W11 原型评审    ── 必须能走完「浏览→下单→支付」并演示 2～3 个防护点
W12 互打补洞、补 AI/IM
W13 攻防报告、展示彩排
W14 最终展示    ── 演示 + 渗透报告 / 攻击链
```

中间的 W2、W7、W9、W10、W12、W13 **没有单独得分项，但决定后面那次评审能不能过。**

## 第一周｜需求构思及描述（得分）

**目标：** 一页纸讲清「给谁用、解决什么、做哪些、故意不做什么」。老师要的是方向，不是接口列表。

### 建议文稿结构（8～12 页或等价 Markdown）

1. **背景**：校园闲置物品、信息不对称、议价成本。
2. **用户**：在校学生（买家 / 卖家）；不做校外商家、不接真实支付。
3. **核心场景（只写 5 条，写透）**
   - 注册登录（校园场景，可用学号或用户名，不必真对接教务）
   - 发布二手（图、价、成色）
   - 浏览与搜索
   - 下单与模拟支付
   - AI 定价建议 + 议价客服（题目硬性）
4. **智能点**：定价如何输入（标题/成色/参考价）、议价机器人的边界（不能替用户承诺发货）。
5. **安全作为需求，而不是附录**：明确要防价格篡改、越权、超卖、支付绕过、SQL 注入、XSS。这是题目里的对抗清单，构思阶段就要写进范围。
6. **范围外**：真实支付宝/微信、微服务、小程序（已选 Vue3 Web，方便对方渗透也方便你们部署）。
7. **技术选型一句话**：Spring Boot + Vue3 + MySQL + Redis + OSS + 大模型 API。
8. **成功标准**：第 11 周能演示闭环；第 14 周能演示至少一条攻击失败（你们防住）和一条对对方的攻击（若赛制要求互打）。

### 本周开发（不要为 0）

- 全员按 [SETUP.md](./SETUP.md) 把仓库跑到 `/api/health` 为 UP。
- 画出 **1 张手绘或 Figma 主路径**：首页 → 商品详情 → 下单 → 模拟支付成功页。

### 完成标准

- 文档能回答：用户是谁、主路径是哪 5 步、安全需求有哪些、明确砍掉了什么。
- 每人本地能启动前后端。

## 第二周｜调研与范围冻结（无单独得分，服务 W3/W5）

**目标：** 计划书和 SRS 不再拍脑袋。

- 拆 **用例表**（名称、参与者、前置、主成功场景、失败分支）。至少覆盖：注册、登录、发布、下单、支付、AI 定价、议价。
- 每人找 1 个同类产品，只记 3 点：人家怎么下单、怎么防重复购买、有没有聊天。禁止整仓抄代码。
- 确认云服务器、OSS、大模型 Key 的负责人（密钥不进仓库）。
- 组长出 **功能优先级**：
  - P0（第 11 周必须）：注册登录、商品 CRUD 的最小集、下单扣库存、模拟支付、服务端算价。
  - P1（第 14 周尽量）：IM、AI 定价、AI 议价。
  - P2（有余力）：搜索筛选、评价、管理端。

IM 和 AI 是题目要求，所以标 P1 不是可以不做，而是 **原型评审可以先用「半成品」**（例如议价先 HTTP 一问一答，不一定上 WebSocket）。第 14 周必须能看出「智能」和「能聊天或等价客服」。

## 第三周｜项目计划书（得分）

**目标：** 老师能从计划里看出你们知道 14 周怎么活下来。本文可直接改成提交版，再补：组员名单、实际周历日期、甘特图截图。

### 计划书建议目录

1. 项目概述与目标（从 W1 浓缩）
2. 组织与分工（用上面角色表，写到人）
3. 进度计划（用本文「总览」+ 下面各周「完成标准」）
4. 里程碑与交付物（对应 8 个得分点 + 中间检查）
5. 技术路线与仓库结构（链到本仓库）
6. 质量与安全计划：每个迭代结束用 Burp 打一次自己的接口
7. 风险：新手 git 冲突、云服务器被扫、Key 泄露、对方渗透、AI 配额。对策写具体（例如 Key 只放 local 配置；超卖用一条 SQL）。
8. 沟通：周会、PR 需 1 个 approve。

### 本周开发

- 定 **API 草稿一页纸**：路径、谁能调、成功/失败码。不求完整，求下单和支付先写清。
- 前端把 W1 的主路径做成可点的空页面（假数据即可），给立项 PPT 截图。

### 完成标准

- 计划书有分工、有周次、有 P0/P1、有风险。
- 甘特图或表格能贴进 PPT。

## 第四周｜立项（得分）

**目标：** 答辩 8～12 分钟能讲完，问答不崩。

### 立项材料

- PPT：问题 → 方案 → 架构一页（单体 + OSS + 云主机）→ 进度 → 风险 → 演示健康检查或空页面。
- 一页「已具备」：仓库、云服务器、OSS、分工。
- 准备老师可能问的：为什么不用小程序、如何防超卖、支付是不是真的（回答：模拟，但状态机是真的，这正是对方会打的点）。

### 本周开发

- 接入 MySQL（云库或 Docker），执行 `sql/init.sql`。
- 开始 **注册登录**（鉴权角色主写）：BCrypt 存密码、登录发 JWT。不要求完善资料页。

### 完成标准

- PPT 能脱稿讲。
- 库表在云上或 Docker 里真实存在。
- 登录接口至少能用 curl 打通（即使前端还没接）。

## 第五周｜需求规格说明书（得分）

**目标：** SRS 让第 6 周评审「审得动」，设计阶段不再改范围。

### SRS 建议目录（按用例写，不要按技术组件写）

1. 引言：目的、读者、术语（订单状态、模拟支付、越权）。
2. 总体描述：产品视角、用户、约束（公网、无真实支付）。
3. 功能需求：每个 P0/P1 用例：编号、描述、输入、输出、异常。
   - 下单：明确「金额以服务端商品现价为准」。
   - 支付：明确合法状态迁移。
   - 库存：明确并发两人同时买一件时只一人成功。
4. 非功能：性能不作重点；**安全需求单独成章**，把题目 6 类漏洞写成「应满足 / 应拒绝」的条目。
5. 接口需求：对外 REST 列表（可仍是草案，但路径稳定）。
6. 数据需求：用户、商品、订单、聊天字段说明（可引用 `sql/init.sql` 再补充）。
7. 验收标准：与第 11、14 周演示脚本对齐。

### 本周开发

- 登录接到前端：能注册、登录、带 token 调一个 `/api/users/me`（可先返回用户名）。
- 商品表开始用：发布接口可以还是半成品，但字段要和 SRS 一致。

### 完成标准

- 每个 P0 用例有编号和验收句。
- 安全 6 条都写成可测试的需求（例如「篡改下单请求中的 amount 必须失败」）。

## 第六周｜需求评审（得分）

**目标：** 开会审 SRS，留下纪要。评审后 **P0 冻结**，再改必须组长点头。

### 会前

- 提前 48 小时把 SRS 发给组员（最好也给老师/助教）。
- 准备争议清单：要不要 IM 上 WebSocket、支付超时怎么取消、AI 失败时的降级（显示「建议价暂不可用」）。

### 会上（建议 60 分钟）

1. 组长过范围和 P0/P1。
2. 逐条过安全需求（这是评审加分项，别当附录翻过）。
3. 记录：保留 / 修改 / 砍掉。

### 会后

- 24 小时内出 **评审纪要**（决议 + 修改点 + 责任人）。
- SRS 改一版「评审后」。

### 本周开发（评审不是停工）

- 商品列表 + 详情（可先本地图，OSS 本周或下周接）。
- 前端商品列表页能看到库里的数据。

### 完成标准

- 有纪要文件。
- 演示：登录后能看到至少一个商品（假数据也行）。

---

## 第七周｜设计草稿 + 登录稳定（无单独得分，服务 W8）

**目标：** 设计说明书不是空文；代码结构已经对得上模块图。

- 画出：部署图（浏览器 → Nginx → Spring → MySQL/Redis/OSS）。
- 画出：订单状态图（与 `PENDING_PAY / PAID / CANCELLED / COMPLETED` 一致）。
- 写出：下单时序（谁算价、何时扣库存、失败如何回滚）。
- 代码：JWT 过滤器、统一错误 JSON、OSS 上传封面（鉴权 + 交易配合）。

### 完成标准

- 设计草稿能贴进 W8 文档。
- 未登录调 `/api/orders` 返回 401；登录后身份能从 token 解析出来。

---

## 第八周｜软件设计规格说明书（得分）

**目标：** 说明「系统怎么造」，和 SRS 的「要什么」对应。

### 设计说明书建议目录

1. 总体架构（单体、模块包名与仓库一致）。
2. 模块设计：auth / goods / order / pay / im / ai / common。
3. 数据库设计：ER 或表说明、索引、为何 `stock` 要条件更新。
4. 接口设计：REST 一览、鉴权、幂等（支付回调只认服务端）。
5. 关键算法：扣库存 SQL、金额计算、订单号生成。
6. 安全设计：逐条对应 SRS 安全需求的实现位置（哪个类、哪条 SQL）。
7. 前端结构：页面与路由（即使当时路由还少）。
8. 部署：云主机、OSS、配置项（不写真实密码）。

### 本周开发

- **下单 P0 打通**：只传 `goodsId + quantity`，服务端算价，`stock >= n` 才成功。
- 用两个浏览器或脚本同时下单同一件库存为 1 的商品，确认只有一单成功。把结果截图进设计文档「验证」小节——老师会喜欢。

### 完成标准

- 文档有状态图、下单时序、安全对照表。
- 超卖实验至少做过一次并记录。

## 第九周｜商品与订单补全（服务 W11）

- 发布 / 下架 / 只能改自己的商品（越权：改别人的 id 必须 403）。
- 订单列表：买家只能看自己的。
- 前端：详情 → 确认订单页（页面上可以显示价格，提交时 **不要把价格当权威参数**）。
- 安全角色用 Burp 改 `amount`、改 `goodsId` 各打一次，记进共享表格。

### 完成标准

- 主路径到「生成待支付订单」可演示。
- 越权、改价各有一条测试记录。

---

## 第十周｜模拟支付 +（IM 或 AI 先做完一个）（服务 W11）

**支付（P0，必须在 W11 前完成）**

- `PENDING_PAY → PAID` 只允许服务端接口推进。
- 拒绝：已支付再付、客户端 `paid=true`、跳过待支付。
- 简单「支付页」：点确认即调 mock 接口（可加 2 秒延迟装一下）。

**P1 二选一本周必须可演示（另一个 W12 补）：**

- IM：买卖双方文字记录（可先轮询，W12 再升 WebSocket）。
- AI：发布时建议价 **或** 议价对话其中一项。

### 完成标准

- 演示脚本能从注册走到「支付成功」。
- P1 至少一项能在评审时点开。

---

## 第十一周｜原型系统评审（得分）

**这是代码的第一道生死线。** 评审当场按脚本走，不要靠口头说「其实已经实现了」。

### 必须能现场做的演示脚本（约 8 分钟）

1. 注册两个号：卖家、买家。
2. 卖家发布一件商品（有图更好）。
3. 买家下单；展示订单金额来自服务端。
4. 模拟支付成功，订单变为已支付。
5. **安全点选 2 个演示**（提前录好或现场 Burp）：
   - 改请求里的价格，下单失败或金额不变。
   - 两个请求抢同一件库存，只有一单成功。
6. 若 IM/AI 已有：加 1 分钟点一下即可。

### 评审材料

- 原型说明 3～5 页：实现了 SRS 的哪些编号、未完成的 P1、已知问题。
- 部署方式：本机演示或云主机 URL（云上更像对抗环境）。

### 完成标准

- 脚本不中断。
- 对应 SRS 的 P0 条目能勾选。
- 已知问题清单诚实（比现场翻车分高）。

---

## 第十二周｜互打补洞、补 P1

- 按题目清单自测：越权、支付绕过、SQL 注入（搜索框、排序字段）、XSS（商品描述）。
- 修 W11 评委或自己踩到的洞。
- 补完 IM 与 AI 中缺的那块。
- 开始写 **渗透测试笔记**（日期、接口、请求、结果、是否修复）。这就是第 14 周报告的素材，不要最后一周回忆。

若赛制是两组互打：本周约定交换 URL 的时间，先打自己再打对方。

---

## 第十三周｜报告与彩排

- 整理《渗透测试报告》：范围、工具（Burp）、发现、复现步骤、修复、复测。
- 准备一条 **攻击链叙述**（例如：未授权访问订单 → 枚举 id → 越权；或对方若有改价则你们能打通）。自己系统要用「攻击失败 / 已被修复」来展示防御。
- 全组彩排最终展示两遍，卡时间（通常 10～15 分钟 + 问答）。
- 检查仓库：没有 Key、没有 `application-local.yml`、README 能让助教按 SETUP 跑起来（或给演示 URL）。

---

## 第十四周｜最终展示（得分）

### 展示建议结构

1. 题目与范围（1 分钟）
2. 现场走交易闭环（3～4 分钟）
3. 智能功能（定价/议价）（1～2 分钟）
4. 安全：防住了什么、怎么防的（2～3 分钟，对着设计文档的对照表）
5. 若有互打：对对方的发现（注意别现场把对方打崩造成纠纷，按老师规则）
6. 总结与分工（1 分钟）

### 交付包

- 可运行系统（云 URL 或打包说明）
- 设计/需求最终版（可与 W5/W8 一致并标注变更）
- 渗透报告
- 演示 PPT
- 源码仓库（public 注意密钥）

| 能力 | 第 11 周原型 | 第 14 周最终 |

| 发布/浏览商品 | 必须 | 必须 |
| 下单服务端算价 | 必须 | 必须 |
| 条件更新库存 | 必须并能演示 | 必须 |
| 模拟支付状态机 | 必须 | 必须 |
| 越权校验 | 至少订单或商品一处能演示 | 清单 6 类都要能讲 |

| IM | 可半成品 | 必须有可用形态 |
| AI 定价+议价 | 至少一项 | 两项都要能演示 |
| 互打报告 | 有测试笔记即可 | 正式报告 |

## 风险与缓冲

| 风险 | 对策 |
| --- | --- |
| 第 11 周前还在改需求 | W6 冻结 P0；新想法进 P2 |
| 新手 git 冲突 | 按模块分包；一天一 PR；先 pull 再开发 |
| 8080 被本机其它项目占用 | 改端口或先关掉占用进程 |
| AI 调不通 / 没钱 | 准备固定示例回复作降级，文档写明 |
| 互打把演示环境打挂 | 演示用单独账号+备份库；前一晚冻结部署 |
| 计划书/SRS 临时抱佛脚 | 每周五把当周文档段落写进 `doc/`，不要堆到截止前一夜 |

## 建议的每周检查问题（周会用）

1. 本周得分文档或代码，是否已经能给别人看？
2. P0 有没有人在改别人的模块？
3. 这周有没有用 Burp 或 curl 打过自己的接口？
4. 密钥有没有进 git？
5. 离下一个得分点还差哪一条「完成标准」？
