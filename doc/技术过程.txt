4. 技术过程

4.1 方法、工具和技术

本项目采用模块化单体与迭代开发相结合的方法。后端为一个 Spring Boot 进程，按业务划分为认证、用户、商品、订单、支付、即时通讯、智能定价与公共能力等模块，模块之间通过接口协作，不拆成微服务。前端是原生微信小程序，放在 campus-trade/miniprogram，作为学生使用入口。需求、设计与实现按课程节点分阶段交付：先冻结范围与主路径，再完成注册登录、商品、下单与模拟支付闭环，最后补齐站内沟通、建议价与安全测试。范围变更须经组长确认后再改接口与文档，避免做到中途推翻主流程。

编程语言与运行环境如下。后端使用 Java（JDK 17）与 Spring Boot 框架，数据访问采用参数化查询，关系数据存放在 MySQL，缓存、占位与限流使用 Redis。前端页面用微信小程序的页面文件编写，页面登记在 app.json，网络请求使用 wx.request。智能定价与议价调用大模型 API，只生成建议价与话术；成交金额由服务端按商品编号重算，模型输出不写入订单。教学场景不接入真实支付、不建立用户余额表，支付按状态机模拟：待支付可变为已支付或已取消，已支付可变为已完成，客户端不得自行标记支付成功。

开发与协作工具如下。代码托管使用 GitHub，主干不直接推送，功能在分支上开发，经拉取请求合并。后端构建使用 Maven，本地数据库与缓存可用 Docker 启动。接口调试与回归使用 Apifox。安全测试使用 Burp Suite，并对照 OWASP Top 10 与业务逻辑类风险（价格篡改、越权、并发超卖、支付绕过、注入、跨站脚本）设计用例。小程序使用微信开发者工具导入 campus-trade/miniprogram 进行联调；开发期允许访问本机接口，正式发布前再配置合法域名。密钥、数据库口令与微信 AppID 只放在本机配置中，不进入版本库。

团队按职责划分，避免同一模块多人并行改同一目录。组长负责范围、进度、评审与答辩组织。后端主责登录与身份、商品、即时通讯服务端、Git 规范与功能测试集合。后端核心负责订单事务、库存扣减、模拟支付与状态机，并负责攻防演示与技术答辩。前端分别负责交易相关页面与浏览、登录相关页面，文档与界面规范另有专人整理。接口字段以 Apifox 为准，前端不自行增加成交价或支付结果字段。

质量策略写进实现约定并在评审中检查：下单请求只提交商品与数量；库存使用带条件的更新，更新行数为零则失败，避免一件商品卖出两次；查询与修改订单、商品、会话时核对当前登录用户；用户输入与模型文案按文本展示，不按 HTML 渲染。上述策略同时作为安全测试的通过标准。

4.2 软件文档

项目文档放在仓库 doc 目录及课程要求的交付件中，随阶段更新，并与当前实现保持一致。不把尚未实现的能力写成已完成功能。

计划编写并维护的文档如下。

（1）需求类：《需求构思及描述》《软件需求规格说明书》。写明使用对象、功能、校园场景约束，以及安全需求。需求评审后形成冻结版本，之后的变更记入评审纪要。

（2）计划与设计类：《软件项目计划书》、《软件设计说明书》。设计说明书说明架构、模块边界、主要数据表、接口、订单状态机，以及缓存与数据库以谁为准。概要与详细设计可按课程模板分册，内容不重复堆砌。

（3）测试与安全类：《软件测试计划》及 Apifox 接口集合；《渗透测试报告》。测试计划覆盖成功路径、未登录、越权与错误参数；渗透报告只针对本组系统。

（4）工程说明：仓库内的启动说明、架构约定、数据库脚本说明。供组员在本机运行后端与小程序，不替代课程正式文档。

同行评价按文档类型安排，不流于形式。需求规格在需求评审会上由全组对照可检查条目评议，重点看安全需求能否测试、是否写入做不到的功能。设计说明书在设计阶段由后端与前端对照接口互审，重点看下单字段、状态转移和权限是否与约定一致。代码以拉取请求为同行评价：至少一人审阅后再合并，关注越权、是否信任客户端价格、是否提交密钥。测试用例由编写接口的人与测试负责人交叉查看。渗透报告在复测通过后由组长与攻防负责人共同确认，再作为课程材料提交。评价意见留在评审记录或拉取请求评论中，不另建无法追溯的聊天结论。

4.3 用户文档

用户文档面向两类人：在校学生（买家与卖家）和课程演示中的管理员。不单独建设对外网站或大型在线帮助系统。文档与界面同时准备，在原型评审前给出主路径说明，在最终展示前与真实界面核对一遍。

学生用户文档以《用户使用说明》为主，说明如何完成校园身份注册与登录、浏览与按楼栋查找、发布商品并填写价格、查看详情与建议价、站内沟通、下单、模拟支付、确认完成或取消，以及如何举报。说明中写清：页面上的价格仅供查看，成交金额以系统记录为准；聊天中不应交换微信和手机号。小程序关键页面保留简短提示（空列表、失败原因、支付状态），减少只靠长文档才能操作的情况。建议价与系统标价在界面上区分开，避免用户把模型话术当成已成交。

管理员文档单独成节，说明如何查看用户、商品、订单状态与举报记录，以及哪些操作会改变商品或订单。课程阶段若管理功能仅为列表与审核，文档范围与实现一致，不描述未提供的资金结算。

文档由负责界面说明的成员根据可运行页面撰写，接口与状态名称向对应开发人员核对。截图在演示前更新。用户文档与需求规格、设计说明书使用同一套状态名称和模块名称，避免三套说法。

4.4 项目支持功能

配置管理以 Git 仓库为唯一源头。主干受保护，功能在分支开发并通过拉取请求合并。构建产物、依赖目录、本地密钥和微信开发者工具的私人配置不入库。接口变更先改 Apifox 再改代码，使测试集合与实现可对应。数据库脚本放在仓库 sql 目录，表结构变更与代码同一批次提交，避免只在某台机器上改库。

软件质量保证不单独购买过程工具，用约定、评审和回归完成。每个写接口至少具备成功、未登录和错误参数用例；订单与支付相关用例还包含重复支付、金额不一致和库存不足。合并前检查：下单是否多收了价格、支付是否可由客户端改状态、查询是否核对了资源归属、SQL 是否参数化。发现的问题记在测试记录中，由模块负责人修改后再复测，不在未复测时标为已关闭。

验证与确认分三层。确认需求：需求评审检查规格是否覆盖校园身份、就近交易、站内沟通和六类攻击，并明确不做什么（真实支付、用户余额、微服务）。验证设计：设计评审检查状态机、数据归属和接口是否可实现、可测试。验证实现：Apifox 跑通主路径；对同一件商品的并发下单只允许一笔成功；用抓包修改价格、伪造支付结果和越权访问订单，确认被拒绝。攻防演示使用本组环境，不针对外部系统。原型评审与最终展示前按演示脚本完整走通一次，文档、界面与接口不一致时改文档或改实现，不以幻灯片代替可运行结果。
